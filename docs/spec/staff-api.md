# Staff API

The HTTP contract between the staff web app (and the bot's webhook) and `apps/api`. Everything here answers only on
the staff host, under `/api`, and every query runs in the caller's `withActor` transaction, so the database decides
again what they may see and do ([ADR-0002](../adr/0002-authorization-and-data-protection.md)).

## Conventions

- **JSON only**, bodies of at most 64 KB (a CSV import: 1 MB). A field a route doesn't take is refused (`400`).
- **Writes come from the staff app:** every method but `GET` needs `Origin` to be the staff origin, or `403`.
- **Errors** are `{ "error": <code> }`, sometimes with `field` or `constraint`. The staff app shows each in words
  (`packages/i18n`, `errors`). Codes: `signIn` (401, no aal2 session), `forbidden` (403), `notFound` (404),
  `invalid` (400, maybe `field`), `limit` (429), `stale` (409), `taken` (409), `linked` (409), `incomplete` (422),
  `unavailable` (503, not configured), `unexpected` (500), and the route-specific ones below.
- **Ids** are uuids; audit and timeline cursors are strings. Dates are `YYYY-MM-DD`; instants ISO 8601 with offset.
- **Contact details** (emails, phones) appear only in a person's own page and the admin's export, never in lists.

## M1: onboarding

A **person summary**, as lists show one:

```json
{
  "id": "…",
  "name": "Ana",
  "fullName": "Ana Ejemplo",
  "stage": "new",
  "owner": { "userId": "…", "displayName": "…" },
  "province": "…",
  "nextAction": "Llamar el jueves",
  "nextActionDue": "2026-10-20",
  "reasons": ["unassigned"],
  "inCommunity": true,
  "sources": ["airtable"],
  "createdAt": "…"
}
```

`name` is the preferred name, else the full name. Both are null for someone saved with only a phone or an email
(PLAN R37), whom the staff app shows as "Sin nombre"; the same goes for a candidate's `name`. `owner` may be null.
`reasons` are the attention reasons (`packages/domain`, `ATTENTION_REASONS`), in order.

### The forms app's routes

`apps/forms` reaches the API inside the cluster only, never through the gateway, on the API's forms port
(`FORMS_PORT`, 3003), which serves these routes and nothing else. Every call carries the shared secret
in `X-Backoffice-Forms-Token` (compared in constant time) and the visitor's address in `X-Forwarded-For`, as the
gateway gave it to the forms app; the API counts submissions per address. Both run as `pauseai_backoffice_public`.

| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /public/census/form` `{ token? }`                                                                                                                                                                                                                                           | `{ options: [{ id, kind: 'skill' \| 'interest', label }], greeting: string \| null, link: 'generic' \| 'personal' \| 'invalid', wordingVersion }`                                                                                                                                                                                                                                                                  |
| `POST /public/census/submit` `{ token?, startedAt, website, answer: { name, preferredName?, email?, phone?, province?, town?, languages?, options?, skillsOther?, interestsOther?, availability?, howHeard?, pronouns?, consentEmail, consentWhatsapp, consentPrivacy, ageOk } }` | `200 { outcome: 'received' \| 'updated' }` (`received` through the generic link whatever happened to the answer, so it never tells whether an email or phone is known; `updated` through a personal link); `400 { error: 'invalid', field }`; `409 { error: 'invalidLink' }`; `429 { error: 'limit' }`. `website` is the honeypot (must be empty) and `startedAt` the form's load time (at least 3 seconds before) |

## M5: after first use

Additions and changes for steps 3 and 7 of [PLAN M5](../PLAN.md#m5-after-first-use): fewer stages, when and where
from, Discord usernames; the team's WhatsApp messages. Everything else above stands.

- **Stages:** `to_triage` and `talking` are gone; a summary's `stage` is one of `new`, `contacting`, `welcomed`,
  `active`, `dormant`, `unresponsive`, `left`, `discarded`. Older timeline events may still name the old two.
- **A person's summary** adds `arrivedOn` (`YYYY-MM-DD`, or null when nobody knows) and `arrival` (`{ id, label }` or
  null): "Llegó el" and "Llegó por". A timeline event adds `happenedOn` (`YYYY-MM-DD` or null); the timeline is in
  that day's order, else the day it was written. `identities[].kind` may be `discord`.
- **`GET /api/people` and `/api/board`** also take `arrival` (an entry's id, or `none`), `arrivedOn` (`known` or
  `unknown`) and `reason` (one attention reason, such as `unassigned`). `q` also matches a Discord username exactly,
  and a phone by its digits (PLAN R72): `q` written only as a phone, with 6 digits or more once a prefix's leading
  zeros go, matches every stored number with them in it.
- **Where someone lives, and where they're from** (PLAN R74). A person's summary adds `country` (an ISO 3166-1 code, or
  null), their page `originCountry` and `originProvince`. `PATCH /api/people/:id` takes `country` and `originCountry` (a
  code, or null; anything else `400`) and `originProvince`; `POST /api/intake` takes `country`, and `originCountry` and
  `originProvince` (R75); `GET /api/people` and `/api/board` take `country` (a code, or `none` for not said). A Bandeja
  item adds `country`, and a conflict may name `country`, `origin_country` or `origin_province`. The census answer takes
  `country`, `originCountry` and `originProvince`; the CSV import maps `country`, `originCountry` and `originProvince`
  (a country by its code or its name in Spanish or English, else the row is invalid); the people CSV export adds `pais`.
- **`PATCH /api/people/:id`** also takes `arrivedOn` (a date, or null for unknown; never a day to come: `422`),
  `arrivalId` (an entry's id, or null) and `stageOn` (with `stage` only, else `400 invalid { field: 'stageOn' }`):
  the day a stage change happened, which its timeline event carries.
- **`POST /api/people/:id/notes`** and **`/attempts`** also take `happenedOn` (a date, never a day to come: `422`).
- **`POST /api/people/:id/identities`** takes `kind: 'discord'` too (2 to 32 lowercase letters, digits, `_` and `.`,
  never `..`; a leading `@` and capitals are fine).
- **`POST /api/intake`** also takes `discord` (enough without a name, a phone or an email; `400 invalid { field:
'discord' }` if it isn't one), `arrival` (an entry's id) and `arrivedOn` (a date; null when nobody knows; left out,
  today).
- **`GET /api/arrival-channels`** (onboarding staff and admins): `{ channels: [{ id, key, label, active, position }] }`,
  in order. **`POST /api/arrival-channels`** `{ label }` (`201 { id }`, `409 taken` for a label in use),
  **`PATCH /api/arrival-channels/:id`** `{ label?, active? }` (`204`) and **`PUT /api/arrival-channels/order`**
  `{ ids }` (`204`, `409 changed` if they aren't exactly the list): admins only.
- **`GET /api/panel`** adds `arrivalsByChannel: { channels: [{ id, label, active }], weeks: [{ week, counts }] }`
  (counts by entry id, `none` for not said) and `unknownArrival` (people with no arrival day). Weeks and
  `firstContact` go by "Llegó el" and leave out whoever has none; `unassigned` is the "Sin asignar" rule's.
- **CSV imports** map three more fields: `discord`, `arrival` ("Llegó por", by label) and `arrivedOn` (dd/mm/yyyy or
  yyyy-mm-dd; an empty cell in a mapped column means unknown). The export adds `discord`, `llego_por` and `llego_el`.
- **Hoy and the bot's `/unassigned`** list the "Sin asignar" rule's people: new, nobody's, arrived in the last 30
  days.
- **`GET /api/people`** (PLAN R59) adds, on its first page only (no `cursor`), `counts: { total, stages }`: how many
  the filters find, and how many in each stage with the rest of the filters (a stage nobody is in is left out).
- **CSV imports** (PLAN R56) map `joinedOn` ("Entró el"; empty: unknown) and `leftOn` ("Salió el"), a stay in the
  community per row, and `stage` takes `left` (Baja). A mapping needs one of `name`, `phone`, `email` or `discord`
  (`400 invalid`, `field: mapping`), and a row one of them filled; leaving before joining is an invalid `leftOn`. The
  preview adds `joinedOn` and `leftOn`, and its `name` is null for a row without one.

Mensajes ([PLAN M5](../PLAN.md#m5-after-first-use), step 7): the WhatsApp messages written in the staff app, for
onboarding staff and admins; never the bot. A message is the team's, written by admins, or a staff member's own
(PLAN R71), which nobody else sees, admins included.

- **`GET /api/message-templates`**: `{ templates: [{ id, purpose, title, body, bodyNameless, active, mine, version,
updatedAt, updatedBy: { userId, displayName } | null }] }`, the team's and the reader's own (`mine`), by purpose
  (`welcome`, `census_link`), those in use first, one's own before the team's, each in the order they were written
  (the order they're offered).
- **`POST /api/message-templates`** `{ purpose, title, body, bodyNameless?, private }` (`201 { id }`): one's own
  (`private: true`), or the team's (`false`, admins only: `403 forbidden` otherwise), for good. And
  **`PATCH /api/message-templates/:id`** `{ title?, body?, bodyNameless?, active? }` (`204`; `403 forbidden` for the
  team's to someone who isn't an admin; `404` for no such message, or someone else's own). Text is trimmed, and a
  blank `bodyNameless` is none. The database refuses, `422 incomplete` with the rule's name in `constraint`: a
  placeholder the purpose doesn't have or a stray brace (`message_templates_placeholders_check`), a census link's
  message without `{enlace}` in either version (`message_templates_link_check`), and a version for someone without a
  name that names them, or one for a message without `{nombre}` (`message_templates_nameless_check`); the version is
  optional (PLAN R76), and either text is up to 10,000 characters. A
  title in use for the purpose, among the team's or among one's own: `409 taken`. Every change to `body` or
  `bodyNameless` adds a version; the purpose and version can't be written. Never deleted: `active: false` retires
  one.
- **`POST /api/people/:id/attempts`** also takes `templateId` and `templateVersion`, both or neither: the message
  that went out, one the template has had and the writer sees (`422` otherwise).
- **`POST /api/people/:id/census-link`** takes an optional body `{ templateId? }`: the census link message to write it
  in, else the first in use (one's own before the team's), else the code's own. `409 stale` when the one asked for is
  retired, isn't a census link's, or isn't one the writer sees. The link records the message and its version, and
  `/sent`'s contact attempt names them.

Step 6, outreach's private records, "Solo yo" ([outreach §6](outreach.md#6-private-records-solo-yo-plan-m5-step-6)):

- **Contacts and organisations** take `private` on `POST` (`true`: the actor's alone) and on `PATCH` (`false`
  shares it with the team; `true` on a team record is `409 shared`). Their summaries, pages and lists carry
  `private`; lists take `visibility` (`private`: one's own; `team`: the team's). A private record is someone else's
  is `404`, to an admin too. A team contact in a private organisation is `409 organisationPrivate`.
- **Notes** (`POST …/contacts/:id/notes`, `POST …/organisations/:id/notes`) take `private: true`, for the writer
  alone; on a private record every note is. Timeline events and notes carry `private`.
- **`GET /api/outreach/contacts/:id/matches`**: `{ contacts: [summary] }`, team contacts that share an email or the
  phone with this one, to merge it into. **`POST /api/outreach/contacts/:id/merge`** `{ into, shareHistory? }`: a
  private contact's own person merges it into that team contact: `204`; `409 stale` if either isn't what it should
  be. **`shareHistory: true`** ("Compartir también mis notas", PLAN R52), on a merge or with `private: false` on a
  `PATCH`, takes the record's history while private (notes and events) to the team as it's shared.
- **`POST /api/outreach/campaigns/:id/targets`** adds team contacts only (a private one is left out of `added`).
- **`GET /api/outreach/rights?q=`** (admins): `{ contacts: [{ id, orgDisplay, personName, private }] }`, the contacts
  whose email, phone or name is exactly `q`, private ones too. **`GET /api/outreach/contacts/:id/export`**
  (admins): everything kept about one, as a JSON attachment, recorded as an export (`contact_json`); `404` if there
  is none. Erasure (`POST …/contacts/:id/erase`) reaches private ones by id too.
- **`GET /api/staff/private-records`** (admins): `{ records: [{ userId, contacts, organisations, notes }] }`, for
  each deactivated member who left private records, how many. **`POST /api/staff/:userId/private-records`**
  `{ to }` (admins): hands them to `to`: `{ moved }`; `409 stillActive` (the account is active); `409 heir` (`to`
  isn't active in outreach nor an admin).

## M3: outreach

Outreach staff and admins, through the staff app ([outreach spec](outreach.md)); never the bot. Erasing a contact
and importing a campaign are for admins. Nothing here sends mail: a letter comes back as text and a `mailto:` link
for the owner's own mail client, and "Sí, enviado" records that it went.

A **contact summary**, as lists show one (no email or phone, as for people):

```json
{
  "id": "…",
  "orgDisplay": "Sindicato Ejemplo — Aragón",
  "organisation": { "id": "…", "name": "Sindicato Ejemplo", "kind": "union" },
  "personName": "Berta Ejemplo",
  "role": "Secretaría general",
  "tier": "A",
  "territory": "Aragón",
  "sector": "Educación",
  "stage": "identified",
  "owner": { "userId": "…", "displayName": "…" },
  "needsReview": false,
  "hold": false,
  "tags": [],
  "anonymised": false
}
```

`organisation` and `owner` may be null. Enumerations: organisation `kind` is `party`, `union`, `ngo`, `university`,
`media`, `company`, `public_body`, `association` or `other`; relationship `stage` is `identified`, `qualified`,
`contacted`, `engaged`, `ally`, `declined` or `dormant`; target `status` is `pending`, `ready`, `sent`, `replied`,
`meeting`, `declined`, `bounced`, `no_response` or `skip`; `treatment` is `neutral`, `masculino` or `femenino`.

A **letter**, as `renderLetter` writes it (`packages/domain/outreach`):

```json
{
  "ok": true,
  "subject": "…",
  "body": "…",
  "words": 180,
  "sources": ["https://…"],
  "warnings": [
    { "kind": "prose", "issue": { "rule": "phrase", "found": "…", "context": "…", "fatal": false } }
  ]
}
```

or `{ "ok": false, "problems": [...] }`, each problem one of `{ kind: 'needsReview' }`, `{ kind: 'held' }`,
`{ kind: 'noTemplate', tier }` (the campaign has no template for the contact's tier),
`{ kind: 'unknownAnchor', anchor }`, `{ kind: 'unresolved', fields }`, `{ kind: 'prose', issue }`; and a warning
`{ kind: 'long', words, maxWords }` as well as `prose`. A letter is sent **with** its handover:
`{ letter, to: [email], cc: [email], mailto: string | null, whatsapp: string | null, templateVersion: number | null }`
(`mailto` only for a letter that is `ok` and a contact with an email; `whatsapp` a `wa.me` link with the body, when
the contact has a phone).
